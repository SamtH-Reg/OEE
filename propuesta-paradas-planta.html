Resumen ejecutivo

Qué se construye y qué se decide

Tres cosas, en este orden: capturar la parada sin fricción (2 toques, sin escribir), no perder el registro aunque se caiga la red (offline real, no un formulario que falla) y convertir esos datos en decisiones (Pareto, disponibilidad, MTBF por máquina).

2 toques

Abrir una parada: máquina + causa. Cerrarla: máquina + «Reanudar». Sin formularios, sin confirmaciones.

0 pérdidas

Cola local en IndexedDB con identificador único por registro: la tablet sigue trabajando días sin red y sincroniza sola.

9 de 18 causas

En la muestra de 14 días, 9 causas concentran el 80% del tiempo muerto. Ese es el informe que cambia las reuniones.

Decisiones que conviene discutir antes de codificar

DecisiónElecciónPor qué
Motor de basePostgreSQL (Neon) Índices parciales, timestamptz, funciones y ventanas analíticas resuelven el Pareto y la sincronización en la propia base. MySQL obliga a simular varias de esas piezas.
ArquitecturaMonolito modular Una planta, cuatro áreas, ~20 tablets. Microservicios acá solo agregan latencia, despliegues y modos de falla. Los módulos quedan separados por dominio para poder extraerlos después.
TabletPWA, no app nativa Un solo código para tablet, PC de supervisión y celular del jefe de turno. Se actualiza sin pasar por tienda y el offline se resuelve con Service Worker + IndexedDB.
Identidad del registroUUID generado en el dispositivo Es lo que hace la sincronización idempotente: si el envío se reintenta 40 veces, la base guarda una sola parada.
Paradas planificadasMarcadas en el catálogo de causas Un lavado de línea no es tiempo muerto. Sin esa distinción, el Pareto acusa a Operaciones de un tiempo que estaba planificado.
BorradoNunca. Se anula con motivo El historial es el activo. Toda corrección queda auditada con usuario, fecha y campos cambiados.
NOTA

El requerimiento original decía «PostgreSQL o MySQL». Se entrega PostgreSQL porque el proyecto ya existe en Neon y porque tres requisitos duros (una sola parada abierta por máquina, idempotencia de sincronización y Pareto acumulado) se implementan en menos código y con más garantías. El anexo 8.1 lista los cambios exactos para portarlo a MySQL si fuese obligatorio.

01
Modelo de datos

Seis tablas, tres reglas que evitan el desorden

El modelo pedido (áreas, máquinas, categorías, causas, turnos, paradas) se mantiene tal cual. Se agregan cinco columnas y una tabla de auditoría que son las que sostienen la operación real: uuid_cliente, estado, es_planificada, registrado_en/sincronizado_en y version.

Las tres reglas que sostienen todo garantizadas por la base

1 · Una parada abierta por máquina

Índice único parcial sobre maquina_id cuando estado = 'activa'. Si dos operadores tocan la misma máquina, la base no permite el duplicado y la función devuelve la parada vigente en lugar de un error.

2 · Un registro, un UUID

uuid_cliente único. La tablet lo genera antes de tocar la red; el servidor hace on conflict do nothing. Reintentos, doble envío y reconexiones no duplican nada.

3 · Nada se borra

Anulación con motivo obligatorio y trigger de auditoría con el diff de columnas. El indicador excluye las anuladas, pero el historial conserva el rastro.

Campos que se agregaron al modelo pedido y por qué

CampoPara qué sirve
uuid_clienteIdempotencia de la sincronización offline. Sin esto, cada reintento de red crea una parada falsa.
estadoactiva / cerrada / anulada. Reemplaza el «hora_fin NULL» como único indicador de estado y permite anular sin borrar.
es_planificadaEn codigos_causa: separa lavado de línea y cambio de producto del tiempo muerto real. Es la diferencia entre un Pareto honesto y uno que culpa a Operaciones.
impacto / porcentaje_afectacionParada total o parcial. Con parcial se registra qué fracción de la línea se detuvo; sin el porcentaje, una parada parcial de 20 minutos se cuenta como si hubiese parado todo.
registrado_en / sincronizado_enDos relojes: el de la tablet (única fuente cuando hubo corte de red) y el del servidor. La diferencia delata tablets desfasadas.
versionControl de concurrencia optimista para las correcciones de supervisor.
nombre_cortoEn maquinas: «Cinta 1» para la tarjeta del tablero, «Cinta Transportadora 1» para los informes. Un nombre largo en una tarjeta de 200 px se corta y el operador toca la equivocada.
01_esquema.sql — tablas, restricciones e índices (extracto)
-- Una sola parada abierta por máquina: la regla que evita el doble registro
create unique index ux_parada_abierta_por_maquina
    on registro_paradas (maquina_id)
    where estado = 'activa';

create table registro_paradas (
    id                        bigint generated always as identity primary key,
    uuid_cliente              uuid        not null default gen_random_uuid(),
    maquina_id                integer     not null references maquinas(id),
    codigo_causa_id           integer     not null references codigos_causa(id),
    turno_id                  bigint      not null references turnos(id),
    hora_inicio               timestamptz not null,
    hora_fin                  timestamptz,            -- NULL = en curso
    impacto                   text not null default 'Total'
                              check (impacto in ('Total','Parcial')),
    porcentaje_afectacion     numeric(5,2),
    comentarios_operador      text,
    comentarios_mantenimiento text,
    estado                    text not null default 'activa',
    origen                    text not null default 'tablet',
    dispositivo_id            text,
    registrado_en             timestamptz not null default now(),
    sincronizado_en           timestamptz not null default now(),
    version                   integer not null default 1,

    constraint ck_uuid_cliente_unico unique (uuid_cliente),
    constraint ck_fin_posterior check (hora_fin is null or hora_fin > hora_inicio),
    constraint ck_estado_horas check (
        (estado = 'activa'  and hora_fin is null) or
        (estado = 'cerrada' and hora_fin is not null) or
        (estado = 'anulada')
    )
);

El script base (691 líneas, comentado, con vistas, funciones y triggers) está en sql/esquema_paradas.sql, más las migraciones 002 a 006 (turno automático, borrado seguro y líneas).

Por qué las duraciones no se guardan como columna

La duración se calcula en la vista v_paradas: extract(epoch from (coalesce(hora_fin, now()) - hora_inicio))/60. Guardarla sería un dato derivado que se desincroniza en cuanto un supervisor corrige una hora. Así, una parada en curso siempre muestra sus minutos reales y una corrección se refleja al instante.

Líneas, tramas y propagación el flujo real de la planta

La planta no es un conjunto de máquinas sueltas: es un flujo. Cada línea tiene su trama (una secuencia ordenada de máquinas) y no todas las líneas usan el mismo equipamiento. Cuando una máquina se detiene, la parada se propaga según el rol que esa máquina tiene en la trama:

Rol en la tramaAlcanceQué se detiene
Cuello de botella (detiene_linea)linea Toda la línea: aguas arriba se acumula producto, aguas abajo falta material.
Máquina intermediaaguas_abajo Solo las máquinas que vienen después en la secuencia; las de atrás siguen con buffer.
Máquina fuera de línea (servicios)maquina Nada más que ella.

El criterio vive en la trama y no en la cabeza del operador: al tocar la causa, el sistema ya sabe si corresponde detener la línea completa. Se mantienen los 2 toques y el criterio queda igual para todos los turnos. La parada se guarda una sola vez: las máquinas arrastradas se calculan en v_maquinas_afectadas, no se duplican registros (si no, el Pareto contaría el mismo evento cinco veces).

create table linea_maquinas (
    linea_id      integer  references lineas(id) on delete cascade,
    maquina_id    integer  references maquinas(id),
    posicion      smallint not null,          -- 1 = inicio de la línea
    detiene_linea boolean  not null default false,  -- cuello de botella
    primary key (linea_id, maquina_id),
    unique (linea_id, posicion)
);

En la app, el panel lateral lista las líneas con su estado y abre la vista en secuencia; el botón Editar trama permite agregar, quitar y reordenar máquinas y marcar el cuello de botella (solo uno por línea).

02
Arquitectura y stack

Monolito modular: un despliegue, cinco dominios separados

La tentación es microservicios. Con una planta, cuatro áreas, ~20 tablets y un solo equipo de desarrollo, un microservicio por módulo significa cinco despliegues, cinco configuraciones de red y cinco formas de caerse — a cambio de una escalabilidad que este sistema nunca va a necesitar (el pico real son 20 tablets enviando un evento cada varios minutos).

Monolito modular: un proceso desplegable, pero con fronteras de dominio explícitas. Si mañana hay que separar la analítica porque corre informes pesados, ya está aislada.

Las tres operaciones críticas (abrir, cerrar, sincronizar) viven en funciones de base de datos, no en el backend. Así, si mañana aparece otro cliente (una app nativa, un script de importación, un Excel conectado), las reglas se cumplen igual. El backend solo autentica y traduce HTTP a SQL.

03
Estrategia offline

La red se cae: el registro no

En una planta pesquera el Wi-Fi no falla «a veces»: falla cuando hay vapor, cuando entra un carro con carga metálica, cuando el AP de la cámara de congelado amanece con hielo. Un formulario web tradicional en ese escenario pierde la parada completa. La estrategia es local-first: la tablet es la fuente de verdad hasta que logra entregar el evento.

PASO 01
Escribir local El toque del operador crea el evento en IndexedDB y actualiza el tablero. Nunca se espera respuesta del servidor.
PASO 02
Encolar El evento entra al outbox con su UUID y un número de secuencia. La UI muestra «sin enlace · 3 pendientes», no un error.
PASO 03
Reintentar Al volver la red (evento online, cambio de pestaña o cada 30 s) se envía el lote en orden, con backoff de 1 s a 5 min.
PASO 04
Conciliar El servidor responde qué eventos ya existían. La tablet borra de la cola solo los confirmados y deja los rechazados con su motivo.

Qué se guarda en la tablet

AlmacénTecnologíaContenido y vigencia
App shellCache API (Workbox) HTML, JS, CSS e íconos. Estrategia stale-while-revalidate: abre al instante y se actualiza en segundo plano.
CatálogoIndexedDB · tabla catalogo Áreas, máquinas, categorías, causas y turnos. Se descarga al iniciar sesión y se refresca por ETag o al cambiar de turno. Sin catálogo no se puede registrar: por eso se valida antes de habilitar el tablero.
OutboxIndexedDB · tabla outbox Eventos pendientes: id, tipo (abrir/cerrar/comentario), payload, seq, intentos, ultimo_error.
Estado del tableroIndexedDB · tabla maquinas Estado optimista por máquina, derivado de los eventos locales. Es lo que ve el operador.

Las cinco reglas que hacen que no se duplique nada

  1. UUID en el dispositivo, no en el servidor. Si el servidor lo generara, un reintento (la respuesta se perdió pero el insert ocurrió) crearía una segunda parada.
  2. Envío en orden por secuencia. La apertura siempre llega antes que su cierre. Aun así el servidor tolera el desorden: fn_sync_lote ordena por hora de inicio y reconcilia.
  3. Una sola parada abierta por máquina. Si llega una apertura cuando ya hay otra abierta, la anterior se cierra en el instante de la nueva. No quedan dos «en curso» para siempre.
  4. Confirmación explícita por evento. La tablet no borra la cola completa cuando el POST devuelve 200: borra solo los UUID que el servidor confirmó.
  5. Sin cierre de sesión con cola pendiente. El botón de salir se bloquea (o advierte) si hay eventos sin sincronizar. Es la causa más común de pérdida de datos en apps offline.

Conflictos: quién gana

SituaciónReglaResultado
Dos operadores abren la misma máquinaLa segunda apertura devuelve la parada ya abiertaUna parada, un dueño, sin mensaje de error en pantalla
Comentario editado en dos tabletsGana el de mayor version; empate → el más recienteSe conserva el último texto y queda el diff en auditoría
Supervisor anula mientras la tablet cierraLa anulación gana; el cierre se rechaza con motivoEl registro queda anulado y auditable, no resucita
Parada creada offline y corregida despuésLa corrección es un evento nuevo con su propio autorHistorial completo, nunca sobrescritura silenciosa

El reloj es el punto débil (y cómo se controla)

Una tablet sin red y con la hora corrida arruina el indicador. Tres medidas:

  • NTP en la tablet y modo kiosco que impide cambiarla a mano.
  • Latido cada 60 s con la hora del servidor: si el desfase supera 2 minutos, se muestra un aviso al supervisor y queda registrado en dispositivos.
  • Dos marcas de tiempo por fila: registrado_en (tablet) y sincronizado_en (servidor). El informe puede filtrar por desfase si hiciera falta.
~200 bytes

Una parada completa en la cola local.

~2 MB / año

48 h de prueba

Protocolo de aceptación: tablet en modo avión dos días, luego reconexión y conciliación sin pérdidas.

OJO

No usar localStorage para la cola. Es síncrono (congela la UI), tiene ~5 MB, y el navegador lo puede borrar sin aviso. IndexedDB con navigator.storage.persist() es lo mínimo para un dato que no se puede perder.

04
Experiencia del operador

La regla de los 2 toques, sin letra chica

Un operador con guantes de PVC, manos mojadas y la línea deteniéndose no va a completar un formulario de seis campos. Si el registro cuesta, el dato no existe: se anota en un papel al final del turno (o no se anota). Por eso el flujo se reduce a dos toques y cero texto obligatorio.

Abrir una parada

Toque 1: la tarjeta de la máquina (que está verde).
Toque 2: la causa concreta (dentro de una de las 5 categorías).
Al soltar, el reloj corre y la tarjeta pasa a rojo.

Reanudar

Toque 1: la tarjeta roja.
Toque 2: «Reanudar operación», el botón que ocupa media pantalla.
El sistema fija la hora de fin y calcula los minutos.

Anatomía del tablero lo que ve el operador al llegar

  • Encabezado con turno, hora real, estado de la red y contador de pendientes. El operador no necesita saber qué es una cola; necesita saber si su registro ya subió.
  • Tarjetas por área, agrupadas en columnas. Cada tarjeta muestra el nombre corto («Cinta 1»), el código y el estado en texto + ícono + color.
  • Color + forma + palabra. Verde con triángulo = opera; rojo con cuadrado = parada no planificada; ámbar con reloj = parada planificada. Un daltónico y una pantalla con reflejo siguen entendiendo el estado.
  • Rojo muestra causa y hora de inicio, no solo «detenida»: el supervisor que pasa por detrás lo lee sin abrir nada.
  • Panel lateral de líneas: cada línea con su estado (operando / parcial / total). Al elegir una, el tablero pasa a mostrar la secuencia de máquinas, no las áreas: el operador ve el flujo tal como lo camina.
  • Naranja = arrastrada: una máquina detenida por otra muestra «Detenida por X» y se reanuda desde ahí mismo, sin registrar una segunda parada.

Lo que se decidió no hacer: login por operador en cada parada (agrega 2 toques y nadie lo hace), causa obligatoria con texto libre (produce «falla» y «no sé»), y listas de más de 6 causas por categoría (el operador toca la primera). 05
Historial y analítica

Del registro al Pareto, sin planillas paralelas

El historial no es un archivo muerto: es la herramienta con la que el supervisor cierra el turno. Cada mañana revisa las paradas del día anterior, completa lo que el operador no alcanzó a escribir y corrige horarios si hubo un error. Todo eso queda auditado y alimenta los mismos indicadores que ve gerencia.

Vista de historial para supervisores

Filtros

Rango de fechas (por defecto «ayer»), área, máquina, turno, categoría, causa y estado (en curso / cerrada / anulada). Un clic en la fila abre el detalle con los dos comentarios y el historial de cambios.

Edición controlada

El supervisor corrige hora de inicio/fin, agrega comentario de mantenimiento y anula con motivo. No puede cambiar la causa sin dejar rastro: cada campo modificado se guarda en registro_paradas_auditoria con usuario, antes y después.

05_historial.sql — el JOIN que alimenta la tabla editable
select p.id, p.fecha, p.turno, p.area, p.maquina,
       p.causa, p.categoria, p.impacto,
       to_char(p.hora_inicio at time zone 'America/Punta_Arenas', 'HH24:MI') as inicio,
       to_char(p.hora_fin    at time zone 'America/Punta_Arenas', 'HH24:MI') as fin,
       p.duracion_minutos, p.estado, p.comentarios_operador, p.comentarios_mantenimiento
from v_paradas p
where p.fecha between $1 and $2
  and ($3::int  is null or p.area_id = $3)
  and ($4::int  is null or p.maquina_id = $4)
  and ($5::text is null or p.estado = $5)
order by p.hora_inicio desc;

Indicadores y su definición exacta

IndicadorFórmulaPara qué se usa
Minutos de parada por máquina y turno Σ duracion_minutos de las paradas cerradas del turno Saber dónde se fue el turno. Es el primer número que mira el jefe de producción.
Disponibilidad por máquina 1 − minutos_no_planificados / minutos_del_turno Comparar máquinas entre sí y contra su histórico. Una cinta al 66% es una cinta que hay que intervenir.
Disponibilidad de planta Se calcula en minutos-máquina: 1 − Σ paradas / (minutos_turno × nº máquinas) Evita el error clásico de sumar paradas de 5 máquinas contra un turno de 720 minutos y obtener 150% de tiempo muerto.
MTTR Promedio de duración de las fallas no planificadas Qué tan rápido responde mantenimiento.
MTBF (tiempo calendario − tiempo muerto) / nº fallas Cada cuánto falla. Sirve para decidir reemplazo vs. reparación.
Pareto de causas Σ minutos agrupados por causa, ordenados de mayor a menor, con % acumulado Dónde atacar primero. Es la entrada de la reunión semanal de mejora.

Cómo se construye el Pareto

  1. Filtrar un período (mes, semana, turno) y, opcionalmente, un área.
  2. Excluir las causas planificadas: lavado de línea y cambio de producto no son tiempo muerto.
  3. Agrupar por causa y sumar los minutos (no contar eventos: una causa frecuente y corta puede importar menos que una rara y larga).
  4. Ordenar de mayor a menor y calcular el porcentaje acumulado.
  5. Cortar donde el acumulado llega a 80%: esas son las causas que explican la mayor parte del problema.
05_pareto.sql — una llamada, todo el cálculo
select posicion, causa, categoria, eventos, minutos, pct_tiempo, pct_acumulado
from fn_pareto_causas(
        '2026-10-26'::timestamptz,
        '2026-11-10'::timestamptz,
        null,     -- área: todas
        false     -- excluir causas planificadas
     );

06
Hardware en planta

El equipo se elige por el lavado, no por la ficha comercial

La tablet vive a un metro de una cinta, con agua a presión, escamas, sal y frío. Un iPad en una funda de silicona dura un mes. El criterio de compra no es «la más resistente del catálogo», sino qué pasa cuando alguien lava la línea con la hidrolavadora a 90 bar y 80 °C.

RequisitoEspecificación mínimaPor qué
ProtecciónIP69K (no IP67) + IK08 IP67 resiste inmersión; IP69K resiste chorro a presión y alta temperatura. En zonas de lavado es obligatorio. IP65/IP67 solo en áreas secas (empaque secundario, oficina de turno).
MaterialAcero inoxidable 316L, sin ranuras ni tornillos expuestos El 304 se pica con la salmuera. Sin superficies donde se acumule materia orgánica.

Dos configuraciones según la zona

Zona de lavado (fileteo, recepción, empaque)

Panel PC industrial IP69K de 10–12" atornillado a un brazo, alimentado por PoE. Sin batería que cargar, sin funda que se rompa, sin tablet que alguien se lleve. Es la opción que menos mantenimiento pide en zonas mojadas.

Zona seca / supervisor

Tablet rugged IP67 con funda y correa, batería reemplazable. Más barata y móvil, sirve para el jefe de turno que se desplaza entre áreas y para el conteo de inventario.

Red y montaje: lo que se subestima

  • Cobertura medida, no estimada: −65 dBm en cada puesto de trabajo, con el equipo encendido y la cámara cerrada. Un AP por cada 2–3 máquinas en zonas húmedas; nunca dentro de la cámara de congelado.
  • VLAN separada para las tablets y QoS para el tráfico de sincronización: la red de planta no debe competir con el video o el ERP.
  • DHCP reservado por equipo: si una tablet cambia de IP, el diagnóstico se vuelve adivinanza.
  • Cableado por canaleta IP69 y prensaestopas M12; nada de enchufes a media altura sobre una línea que se lava.
ATEX

La sala de compresores de amoníaco es atmósfera potencialmente explosiva. Ahí no va una tablet común ni un panel PC estándar: se usa equipo certificado para la zona (o se deja el registro fuera del recinto, con la máquina visible desde la puerta). Es el único punto del proyecto donde la norma manda sobre la ergonomía.

El pareto y las ventanas analíticas funcionan igual desde MySQL 8.0. Lo que se pierde son los índices parciales y las funciones que devuelven conjuntos, que es justo donde vive la lógica de sincronización.

8.2 · Autenticación y permisos

  • Operador: la tablet se desbloquea con PIN de turno. El token dura 12 h y no da acceso a escritura fuera de /api/paradas y /api/sync.
  • Supervisor: usuario y clave, token de 8 h, acceso a historial y correcciones.
  • Administrador: catálogos y usuarios. Toda escritura de catálogo queda auditada.
  • Si más adelante hay varias plantas, se agrega planta_id a áreas y turnos y se filtra por token. El esquema actual no lo impide.

8.3 · Operación de la base en Neon

  • Rama main = producción. Rama de staging creada desde main para probar migraciones: si algo falla, se descarta sin tocar producción.
  • Migraciones versionadas en el repo (sql/migrations/) y aplicadas por CI.
  • Respaldo: Neon hace point-in-time restore; además, un pg_dump semanal a almacenamiento externo (barato y auditable).
  • Pooling: la app usa el endpoint -pooler; las migraciones, el directo.
  • Monitoreo: alerta si la tabla dispositivos muestra un equipo con pendientes > 0 por más de 30 minutos (red caída o tablet abandonada).
